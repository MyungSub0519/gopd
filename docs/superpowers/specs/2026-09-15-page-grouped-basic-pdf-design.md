# 페이지별 기본 PDF 응답

## 요구와 응답 형식

기본 PDF 응답의 공개 필드는 `Texts`와 `Graphics`만 제공한다. 사용자는 두 필드 모두 페이지별 이중 배열로 구성하는 방식을 선택했다.

```go
type PDF struct {
    Texts    [][]Text
    Graphics [][]Graphic

    details *DetailedPDF
}
```

- `Texts[pageIndex]`와 `Graphics[pageIndex]`는 같은 페이지의 요소를 담는다. 페이지와 요소 인덱스는 0부터 시작한다.
- 각 바깥 배열의 길이는 상세 결과의 페이지 수와 같다. 요소가 없는 페이지도 빈 배열 `[]`로 남긴다. 페이지가 없는 문서는 두 필드 모두 `[]`로 직렬화한다.
- 페이지 안에서 종류별 콘텐츠 실행 순서를 유지한다. Text와 Graphic의 기존 필드 및 공유 글꼴 정보는 유지한다.
- 기본 JSON의 루트 키는 Texts와 Graphics 두 개다. 페이지 메타데이터, 이미지, 진단 및 종류 사이의 그리기 순서는 `Details()`의 기존 상세 결과에 보존한다.

## API와 오류 처리

`ParsePDF(path) (*PDF, error)`와 `Details() *DetailedPDF`의 시그니처는 유지한다. 상세 분석은 계속 먼저 수행한다. 이번 변경은 기본 결과의 구성 변경이며 메모리 절약 모드가 아니다.

기존 `PDF.Pages`, `PDF.Images`, `PDF.Diagnostics` 필드 사용과 평면 배열로의 Texts/Graphics 접근은 새 구조로 이전해야 한다. 기존 공개 보조 타입은 이번 변경에서 제거하지 않는다. 상세 API의 평면 배열과 기본 API의 페이지별 배열 인덱스는 더 이상 직접 대응하지 않는다. 상세 페이지의 Items로 해당 페이지의 전역 상세 인덱스를 찾을 수 있다.

기존의 오류 및 부분 결과 반환을 유지한다. 미지원 효과 진단은 상세 결과에서 확인하며, 기본 Text와 Graphic의 해석 상태 필드도 유지한다.

## 변경 범위와 검증

- `basic_model.go`, `basic.go`: 기본 결과를 페이지별 배열로 구성한다. 상세 데이터와 기본 가변 슬라이스의 분리를 유지한다.
- `cmd/gopd`: 상세 결과를 사용해 기존 텍스트 출력, 이미지 포함 요약 및 진단 개수를 유지한다.
- 기본 API와 CLI 테스트: 새 응답 계약에 맞추고 여러 페이지 사이의 빈 페이지, 종류별 순서, 공유 글꼴, 부분 결과를 검증한다.
- 기본 API 문서, 공개 API 문서: 새 접근 방법과 마이그레이션을 설명한다. 이전 설계 문서는 이 문서로 연결한다.
- 검증 명령은 `go test -count=1 ./...`, `go build ./...`, `go vet ./...` 및 CLI 실행이다.

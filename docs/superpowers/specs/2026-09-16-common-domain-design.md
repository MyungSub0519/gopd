# 공통 PDF 도메인 분리

## 목표

루트에 나열된 공통 타입과 테스트 준비 코드를 역할별 패키지로 묶는다. 이번 범위는 공통 기반 분리이며, 객체 로더·콘텐츠 인터프리터·폰트 해석기의 패키지 이동은 후속 작업이다.

## 패키지 경계

- `internal/pdfmodel`: 원시 PDF 값, 스트림, 간접 객체, xref, 토큰, 바이트 출처, 파일 구조, 진단, 제한값과 사전 조회·숫자 변환. `Source → Transform → Object → Span` 참조 관계와 비공개 인터페이스 메서드의 구현을 함께 유지한다.
- `internal/geometry`: `Point`, `Rect`, `Matrix`와 변환 계산. 다른 프로젝트 패키지에 의존하지 않는다.
- `internal/pdftest`: 파서에 의존하지 않는 합성 PDF·스트림 생성기. 테스트에서만 가져온다.
- 루트 `gopd`: 사용자 API, 결과 모델, 파싱·해석 구현. 이동한 공통 타입은 `type A = pdfmodel.A` 형태로 다시 노출하고 함수는 위임한다.

`common` 또는 `utils`에 관계없는 기능을 계속 추가하지 않는다. 색상·그래픽 상태·폰트는 콘텐츠 해석 도메인에 남긴다. 테스트는 대상 구현과 같은 패키지에 두며, 테스트만을 위해 비공개 기능을 공개하지 않는다.

## 호환성

기존 import 경로, 공개 타입·상수·함수 이름, 메서드, JSON 필드와 파싱 결과를 유지한다. 별칭을 통해 기존 타입 단언과 구조체 리터럴을 계속 사용한다. 이동한 실제 정의의 패키지는 달라지므로 리플렉션의 `PkgPath` 및 `%T` 출력은 변경될 수 있다. 내부 패키지 경로는 외부 사용자 API가 아니다.

## 테스트 정리와 검증

중복 PDF 작성기를 `pdftest`로 모으고, 루트 패키지에 필요한 파싱 준비 함수는 `test_helpers_test.go`에 둔다. `review_*` 테스트는 필터·객체 경계·xref·폰트·그래픽 상태 파일로 나눈다. 기존 테스트의 검증 내용은 유지한다.

전체 테스트, 빌드, vet와 외부 패키지 API 테스트를 실행한다. 새 외부 의존성은 추가하지 않으며, 기존 문서 변경은 보존한다.

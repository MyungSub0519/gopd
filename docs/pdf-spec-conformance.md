# PDF 표준 구현 지침

GoPD는 Go 네이티브 PDF 라이브러리로서 PDF의 파일 구조와 콘텐츠를 명세에 따라 해석한다. 기능 추가와 버그 수정은 **명세 근거 → 기대 동작 → 테스트 → 구현** 순서로 진행한다. 이 문서는 앞으로의 개발 규칙이며, 현재 구현이 PDF 표준 전체를 준수한다는 선언이 아니다. 현재 처리 계약과 제한은 [리소스 제한](resource-limits.md), 코드 계층은 [기여 안내](../CONTRIBUTING.md)를 따른다.

## 기준 명세와 적용 범위

초기 구현 기준은 PDF 1.7로 정한다. Adobe가 공개한 PDF Reference와 ISO 표준은 판본을 구별하여 참조한다. PDF 2.0은 별도 확장 목표이며, 그 규칙을 PDF 1.7 입력에 일괄 적용하지 않는다.

| 문서 | GoPD에서의 용도 |
| --- | --- |
| Adobe PDF Reference, Sixth Edition, version 1.7 (2006) 및 해당 정오표 | Adobe PDF의 원래 정의, 버전별 도입 이력과 구현 참고 사항 확인 |
| ISO 32000-1:2008, PDF 1.7 | PDF 1.7 준수 판단의 기본 기준. Adobe 공개본을 참조할 수 있다 |
| Adobe Supplement 및 Extensions | 기본 PDF 1.7과 분리하여 확장 이름·BaseVersion·ExtensionLevel별로 지원 여부 관리 |
| ISO 32000-2:2020, PDF 2.0 및 해당 정오표 | PDF 2.0 기능을 구현할 때 적용할 별도 기준 |

공식 문서 입구는 [PDF Association의 명세 아카이브](https://pdfa.org/resource/pdf-specification-archive/)이며, PDF 1.7 기준 문서는 [Adobe 공개 PDF 32000-1 문서](https://opensource.adobe.com/dc-acrobat-sdk-docs/pdfstandards/PDF32000_2008.pdf)에서 확인한다. 아카이브에는 Adobe 1.7 Reference, 정오표와 확장 문서도 연결되어 있다. PDF 2.0 변경 사항은 [PDF Association의 정오표](https://pdf-issues.pdfa.org/32000-2-2020/index.html)에서 확인한다.

명세와 외부 구현이 다를 때 다음 규칙을 적용한다.

1. 대상 PDF 버전과 확장 수준을 먼저 결정한다. 헤더만으로 모든 기능의 의미를 결정하지 말고, 해당 판본의 Catalog 버전 및 Extensions 규칙을 확인한다.
2. 해당 판본의 규범 조항과 적용 가능한 정오표를 우선한다. PDF 1.7 기준에서 Adobe Reference와 ISO 문구가 다르면 ISO 32000-1:2008을 기준으로 차이를 기록한다.
3. 규범 요구, 권고, 예제, Acrobat 구현 참고 사항을 구별한다. Acrobat의 관대한 복구 동작을 필수 표준 동작으로 간주하지 않는다.
4. MuPDF·PDFium·PDFBox 등의 결과는 상호운용성 비교 자료로 사용한다. 다수 구현의 일치만으로 명세 근거를 대체하지 않는다.
5. 정오표는 문서 판본·조항·확정 상태·확인 날짜를 기록한다. 토론 중인 이슈를 확정된 규칙으로 취급하지 않고, PDF 2.0 정정을 1.7에 소급할 때에는 별도 근거를 남긴다.

PDF/A·PDF/UA·PDF/X 적합성, 픽셀 렌더링, 문서 생성·수정, 전자서명 검증은 각각 별도 지원 범위다. 파싱 성공이나 텍스트 추출 성공만으로 이러한 기능 또는 PDF 전체 준수를 주장하지 않는다.

## Go 네이티브와 책임 경계

- 배포되는 라이브러리의 PDF 처리는 Go로 구현한다. CGO, DLL, 외부 PDF 실행 파일을 필수 런타임 의존성으로 추가하지 않는다. 비교 검증용 도구와 race 검사 도구 체인은 이 조건과 구별한다.
- 표준 라이브러리를 우선한다. 외부 Go 의존성은 필요성·라이선스·유지보수 상태·의존성 비용을 검토하고, PDF 파싱 의존성 도입은 기존 [기여 규칙](../CONTRIBUTING.md)을 따른다.
- `internal/syntax`는 바이트와 객체 구문, `internal/document`는 파일·xref·참조·스트림, `internal/pdfmodel`은 공통 표현, 루트 `gopd`는 공개 API와 콘텐츠 의미 해석을 담당한다.
- 구문 계층에서 텍스트를 임의의 UTF-8 문자열로 해석하거나, 의미 계층에서 독자적인 xref 복구기를 만들지 않는다. 기존 계층에 규칙을 구현한다.
- 원본 바이트와 해석 결과를 분리한다. 디코딩·정규화·추론 이후에도 `Source`·`Span`·변환 이력을 통해 입력을 추적할 수 있어야 한다.
- 공개 타입·오류 계약·JSON 표현의 변경은 호환성 영향을 기록한다. 미구현 정책을 이미 존재하는 옵션이나 API처럼 문서화하지 않는다.

| --- | --- | --- |
| 토큰과 객체 | PDF 공백·구분자·주석, 수의 문법과 범위, 이름 escape, literal/hex string, 배열·사전, null, 간접 참조, 중복 키 처리 | `internal/syntax`, `internal/pdfmodel` |
| 파일 구조 | 헤더·trailer·startxref·EOF, xref table/stream, hybrid-reference, 증분 갱신의 우선순위, free entry와 generation, Prev 순환 | `internal/document` |

| 스트림과 필터 | Length와 데이터 경계, 직접·간접 값 제약, Filter 배열 순서, DecodeParms 대응, predictor, 불완전 데이터와 출력 한도 | `internal/document` |

| 콘텐츠 실행 | 연산자별 피연산자·허용 문맥, q/Q·BT/ET 상태, cm과 행렬 합성, 경로·클리핑, Form의 Matrix·BBox·리소스·재귀 | `content*.go`, `graphics_state.go` |

스트림 끝을 단순 문자열 검색으로 찾거나, 글리프 번호를 Unicode로 간주하는 등 명세의 구조를 생략하는 휴리스틱을 정상 해석 경로에 넣지 않는다. 복구가 필요하면 아래 호환성 규칙으로 분리한다. 텍스트 읽기 순서·단어 분리·폰트 대체 같은 추론은 원본에 명시된 정보와 구별하여 제공한다.

## 오류와 호환성 정책

정상 입력 해석과 손상 파일 복구를 구분한다. 새 복구 규칙에는 적용 조건, 명세와의 차이, 진단, 결과에 미치는 영향과 회귀 테스트가 필요하다. 향후 strict/repair 모드를 도입한다면 별도 API 설계를 거친다. 이 문서는 그러한 모드가 이미 구현되어 있다고 가정하지 않는다.

| 상황 | 요구 동작 |
| --- | --- |
| 지원 범위 안의 유효한 입력 | 명세에 맞는 값과 원본 추적 정보를 반환 |
| 구조적으로 잘못된 입력 | 적절한 오류 또는 명시적 복구 진단. 무제한 탐색·무한 반복 금지 |
| 유효하지만 미지원인 기능 | 안전하게 보존 가능한 원본을 유지하고 오류 또는 진단·불완전 표시로 영향 전달 |
| 결과 일부만 해석 가능 | 부분 결과와 완전한 결과를 호출자가 구별할 수 있어야 함 |
| 자원 한도 초과 | `ErrLimit` 반환. 미지원 경고나 조용한 데이터 생략으로 바꾸지 않음 |

알 수 없는 키나 연산자의 처리도 문맥별 명세를 따른다. 모두 거부하거나 모두 무시하는 공통 규칙을 만들지 않는다. 미지원 색 공간·글꼴·암호화 데이터를 임의의 기본값으로 대체한 뒤 완전한 결과로 보고하지 않는다. 결과에 영향을 주는 생략은 그 결과의 완전성에 반영한다.

사전의 누락·null·타입 불일치·미지원 값은 구별하여 검토한다. 현재 null과 중복 키 정책은 [해석 정책](resource-limits.md#interpretation-policy)에 기록되어 있다. 이를 변경할 때에는 명세와 기존 API 영향을 함께 검증한다.

## 자원과 입력 안전성

파일 크기·객체 수·중첩 깊이·참조 순환·디코딩 바이트·반복 콘텐츠 실행·CMap 확장·진단 수를 제한한다. 큰 할당과 반복 작업 전에 길이·오프셋·곱셈·정수 변환을 검증하고, 32비트 환경에서도 오버플로로 검사 범위를 우회할 수 없게 한다.

캐시는 재사용으로 발생하는 모든 비용을 없애지 않는다. 디코딩 결과 저장 비용과 매번 실행되는 콘텐츠·리소스 조회 비용을 구분하여 계산한다. 한도 추가 또는 계산 방식 변경은 [리소스 제한](resource-limits.md)에 반영한다. 자원 제한으로 거부된 입력을 곧바로 표준 위반 문서라고 판정하지 않는다.

PDF의 JavaScript·Launch action·외부 URI·외부 파일 참조는 분석 대상 데이터로 취급한다. 파싱 과정에서 실행하거나 네트워크·로컬 파일 접근을 자동 수행하지 않는다.

## 명세와 테스트 연결

동작을 바꾸는 PR에는 다음 정보를 남긴다. 명세 조항은 판본과 함께 기록하며 페이지 번호만 인용하지 않는다. 중요한 경계 조건에는 코드 또는 테스트에도 근거를 남긴다.

```text
기능 / 요구사항:
기준 문서 / 판본 / 절 / 표:
적용 PDF 버전 / 확장 수준:
적용한 정오표 / 확인 날짜:
명세에서 도출한 기대 동작:
정상 입력 / 경계 입력 / 잘못된 입력의 기대 결과:
구현 파일 / 테스트 이름 / fixture:
미지원 조건 / 복구 동작 / 완전성에 미치는 영향:
공개 API 및 자원 제한 영향:
실행한 검증과 결과:
```

- 버그 수정은 실패를 재현하는 작은 회귀 fixture부터 만든다. `internal/pdftest`와 수작업 바이트 입력을 활용하고, 기대값을 파서 구현 자체로 생성하지 않는다.
- 관련된 null·간접 참조·잘못된 타입·정확한 한도·한도 초과·순환·잘린 스트림을 검증한다. 모든 기능에 무관한 조합을 기계적으로 추가하지 않는다.
- `go test ./...`의 fuzz seed 실행과 실제 fuzz 탐색을 구별한다. 수정한 경계의 fuzz target을 실행하고 발견된 실패는 최소화하여 보존한다.
- 패닉 유무뿐 아니라 객체 값·바이트 범위·참조 해석·상태 복원·진단·부분 결과 표시를 확인한다.
- 다른 PDF 엔진과 결과를 비교할 때 도구 버전, 입력, 비교 항목을 기록한다. 차이가 있으면 명세로 판정하고, 외부 엔진의 출력을 무조건 정답으로 고정하지 않는다.
- fixture 출처와 재배포 조건을 기록하고 개인정보가 담긴 문서를 추가하지 않는다. 표준 문서 자체의 저장소 재배포 여부도 별도로 확인한다.

기본 검증 명령과 race·386·fuzz·정적 검사 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md)를 따른다. 제품의 Go 네이티브 조건은 `CGO_ENABLED=0` 빌드·테스트로 확인하며, race 검사는 지원되는 별도 도구 체인으로 수행한다. 문서만 수정하는 경우에는 링크·내용·diff를 검증하고 코드 테스트 미실행을 명시할 수 있다.

## 지원 상태와 완료 기준

지원 상태는 기능 단위로 `미지원`, `부분 지원`, `검증됨`으로 기록한다. `검증됨`에는 반드시 대상 판본·구체적인 하위 범위·테스트 근거가 있어야 한다. 예를 들어 이미지 사전과 압축 바이트를 읽는 기능과 해당 이미지의 픽셀을 디코딩하는 기능은 서로 다른 항목이다.

기존 README의 제한 사항을 초기 현황으로 사용한다. 새로운 기능의 상태는 구현과 테스트를 확인한 뒤 갱신하며, 제한이 남아 있는 상위 범주를 통째로 지원 완료로 표시하지 않는다. 명세 추적 기록은 해당 PR 또는 기능 문서에 유지한다.

기능 완료를 보고하기 전에 다음을 확인한다.

- 대상 판본과 규범 조항을 확인했는가.
- 선언한 지원 범위의 정상·경계·오류 동작을 테스트했는가.
- 미지원·복구·부분 결과가 호출자에게 드러나는가.
- 원본 추적 정보와 자원 한도를 유지하는가.
- 공개 API·README·관련 문서의 지원 범위가 실제 구현과 일치하는가.
- 실행한 검증과 남은 제한을 구체적으로 기록했는가.
